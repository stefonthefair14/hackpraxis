# 401 / 403 Bypass

## What it is
A `401` (needs authentication) or `403` (forbidden) means a control is standing
between you and a resource. Sometimes that control is enforced in one place
(say, a reverse proxy) while the thing it's protecting lives somewhere else (the
application). When the two disagree about what a request means, you can slip a
request past the guard that the guard thinks is harmless but the app treats as
the real, protected thing.

This tab replays one endpoint through a matrix of known tricks and shows you the
status code and response size for each, next to a plain baseline. **You're
looking for a row that behaves differently** — a `200` where the baseline was
`403`, or a markedly different response size.

## Why the tricks work
- **Spoofed source-IP headers** (`X-Forwarded-For`, `X-Real-IP`,
  `X-Custom-IP-Authorization`, …). Some apps allow "internal" clients and decide
  who's internal by trusting a header a front-end is *supposed* to set. If the
  app reads it without the proxy overwriting it, you can claim to be
  `127.0.0.1`.
- **URL-rewrite headers** (`X-Original-URL`, `X-Rewrite-URL`). On some stacks the
  app routes on these instead of the real request line. You request an allowed
  path (`/`) but set `X-Original-URL: /admin`; the proxy sees `/`, the app sees
  `/admin`.
- **Path & encoding mutations** (`/admin/`, `/admin/.`, `/admin//`, `/admin/..;/`,
  `/%2e/admin`, `/admin%20`). Proxies and application servers normalise paths
  differently. A trailing dot, a doubled slash, a path parameter (`..;/`) or an
  encoded dot can land on the protected handler while the front-end's rule —
  which matched the exact string `/admin` — no longer fires.
- **Method / verb tampering** (`POST`, `HEAD`, `OPTIONS`, …). Access rules are
  sometimes written for `GET` only. If `HEAD` or `POST` reaches the handler, the
  rule never applied.

## How to read the results
- **Compare everything to the baseline row.** The baseline is the plain `GET`.
- A different **status code** (especially `200`, `302`, `500`) is the headline
  signal. `500` can mean you reached code that the front-end normally shields.
- A different **size** at the same status code is subtler but real — the app may
  be returning different content for your mutated request.
- One hit is a lead, not proof. **Confirm by hand**: copy that exact curl, run it
  yourself, and look at the actual body. A `200` with an empty or error body
  isn't a bypass.

## Pitfalls
- A WAF or load balancer may return `200` for *everything* (a block page). Check
  the baseline and a deliberately-bogus request first to learn the "normal" shape.
- Header tricks that "work" against a staging box often fail in production where
  the proxy strips client-supplied `X-Forwarded-For`. That's the system working
  as intended.
- Don't confuse "different size because of a timestamp/CSRF token" with a real
  content change.

## Reporting
If you confirm a bypass, the report writes itself from this tab: the exact
request, the baseline vs. bypass status/size, and the body proving you reached
protected content. That reproducibility is what gets a bounty paid.
